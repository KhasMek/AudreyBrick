# M2 task briefs: the app, on the development machine

**Status: written 2026-11-17, not started. Waiting for the human's go-ahead.**

M2 outcome: one SDL2 program, `audreybrick`, that plays the instrument in real time with the approved button scheme and shows every value on a 1024x768 screen. It is built and tested on the Mac, where the Brick's buttons are bound to a gamepad and to the keyboard. **The same code is what gets cross-compiled for the Brick in M3**; nothing in M2 is Mac-specific.

Decisions this builds on: `docs/CONTROL_SCHEME_PROPOSAL.md` section 0 (approved as a first version on 2026-11-17), `docs/RISKS.md` section 2a, `docs/PLAN.md`.

## Scope of M2

In: tabs LOOP, FILTER, REVERB, DELAY and OUT (volume only); feedback on L2/R2; momentary feedback maximum; the delay switch (held and latched); fine adjust; reset to default; real-time audio out; the always-visible value strip, output meter and CPU meter.

Not in M2 (later milestones): audio input and the INPUT tab (M2b), the safety limiter (M4), presets and the freeze slot (M5), the MOD tab (after sign-off), device packaging, config-file remapping and the exit hotkey for the device (M3). Tabs that are not built yet are not shown.

## Design shared by all three tasks

```
UI thread (60 Hz)                                   audio thread (SDL callback)
  SDL events -> InputMap -> Button events             ButtonControlSource::read()   once per 4 samples
  ControlModel: tab, press/hold timing        ---->     drains the command queue, integrates ramps,
    -> commands (lock-free SPSC queue)                  fills the ControlFrame, publishes values
    -> held-state word (one atomic)            <----  atomics: 11 knob values, switch, meters, CPU
  Renderer draws a UiSnapshot                         AudreyVoice::process()
```

- **Knob values live on the audio side.** Ramps are integrated in `ButtonControlSource::read()` at the 12 kHz control rate, so a held button moves a knob smoothly. The UI thread never writes a knob value directly; it sends commands and reads back the published values for display.
- **Commands** (fixed-size POD, through a single-producer single-consumer ring buffer preallocated at start): `Step{knob, delta}` (a tap), `Reset{knob}`, `SetAll{11 values, switchLatch}` (for presets later), `ToggleSwitchLatch`. If the queue is full the UI drops the command and counts it; the audio thread never waits.
- **Held state** (one `std::atomic<uint32_t>` written by the UI thread): for the two d-pad axes of the current tab, which knob each axis is bound to and its direction (-1, 0, +1); feedback direction; fine flag; feedback-maximum held; switch held. The audio side reads it once per control block.
- **Feedback maximum** does not change the stored feedback value: while held, the frame's `FeedbackGain` is 1.0; on release it is the stored value again. The firmware's own 50 ms smoothing makes both edges click-free.
- **The switch** in the frame is `latch XOR held`.
- **Step sizes and rates** (normalised knob travel, from the approved proposal): tap = 1/128 (fine 1/1024); Frequency tap = 1/56 (one semitone; fine 1/560); feedback tap = 0.5/72 (0.5 dB; fine 0.1/72); held ramp starts 250 ms after the press, begins at 0.1 of travel per second and accelerates linearly to 0.4 per second over 1 s (fine: one eighth of both); feedback ramp is a constant 24/72 per second (fine 4/72). Values clamp to 0..1. All of these constants live in one header so they can be tuned in M4.
- **Start-up state:** every knob at its `ParamTable` default position, switch off, tab LOOP.
- **Engine rate is always 48 kHz.** The audio device is opened for 48000 Hz, float32, stereo, 256 frames, allowing SDL to change only the buffer size, so SDL converts if the hardware runs at another rate.
- **Flush-to-zero** is enabled on the audio thread at the start of the first callback (the FPCR FZ bit on arm64; a no-op with a compile-time note on other architectures). The offline tools are unchanged, so the reference hashes are unaffected.
- **Text** is drawn with an embedded 8x8 bitmap font so the app needs no font library or font file on the device. The font is `font8x8_basic` from https://github.com/dhepper/font8x8 (public domain), vendored as one header under `third_party/font8x8/`.
- **Button names** are SDL GameController names (`A` is the bottom face button in SDL's naming). Which physical Brick button that is gets settled by the device checklist; the binding table is in one place so M3 can make it configurable.
- **Keyboard binding for development:** arrows = d-pad; Q / W = L1 / R1; A / S = L2 / R2; Space = A; B, X, Y = B, X, Y; Left Shift = Select; Return = Start; Escape = quit.

Every worker reads first: `CLAUDE.md`, `docs/PLATFORM_NOTES.md` sections 6 and 7, `docs/PLAN.md` sections 3 to 5, `docs/CONTROL_SCHEME_PROPOSAL.md` section 0, `docs/PARAMETERS.md` section 2, this file's two sections above, `src/core/*.h`, `src/control/ScriptControlSource.h`, the root `CMakeLists.txt`.

**Added after the M2-A review (2026-11-17):** every task also runs `scripts/build_linux_arm64.sh` as part of its verification (Docker must be running). M2-A first failed to build with gcc on Linux because of a header that Apple's library pulled in indirectly; each file must include what it uses. For M2-B and M2-C the container has no SDL2, so it exercises the `AUDREY_WITH_SDL=OFF` path only; a Linux build of the SDL parts is part of M3.

`ControlModel::releaseAll(time)` exists for M2-B to call on window focus loss and controller removal, so no held button stays stuck.

## M2-A: button control logic (no SDL)

```
Goal: The complete control behaviour of the approved button scheme exists as hardware-free,
      SDL-free code: button events in, a ControlFrame per control block out, with tests.

Context: M1 is complete. ControlSource, ControlFrame, Knob, ParamTable and AudreyVoice are in
      src/core. The design is in "Design shared by all three tasks" above and in
      docs/CONTROL_SCHEME_PROPOSAL.md section 0. This task builds the two halves that meet
      at the command queue: the UI-side ControlModel and the audio-side ButtonControlSource.

Scope: src/control/ButtonControlSource.{h,cpp}, src/control/ControlCommands.h,
      src/control/SpscQueue.h, src/control/ControlTuning.h, src/app/Buttons.h,
      src/app/ControlModel.{h,cpp}, src/app/Tabs.{h,cpp}, tests/control/**, and CMake lines
      that add them (a static library audrey_control that links audrey_core; add_subdirectory
      lines only in the root CMakeLists.txt).
Out of scope: anything that includes an SDL header; src/core; src/tools; rendering; audio
      devices; presets; the INPUT, MOD and PRESETS tabs; the safety limiter.

Constraints:
  - ButtonControlSource implements audreybrick::ControlSource. read() and everything it
    calls: no allocation, lock, I/O, logging or waiting; bounded work per call (drain at
    most a fixed number of commands per block).
  - SpscQueue: single producer, single consumer, fixed capacity set at construction,
    wait-free push and pop, trivially copyable element type. Push returns false when full.
  - Buttons.h: enum Button { DpadUp, DpadDown, DpadLeft, DpadRight, A, B, X, Y, L1, R1, L2,
    R2, Select, Start } and a ButtonEvent { Button, pressed }. No SDL types.
  - Tabs: a table describing each tab (name, and for each of the four d-pad bindings
    left/right, up/down, X+left/right, X+up/down, which Knob it moves or none). M2 tabs and
    bindings exactly as in the proposal: LOOP (frequency, body), FILTER (lowpass, highpass),
    REVERB (dry/wet, decay), DELAY (time, mix, and X+up/down = repeats), OUT (up/down =
    volume; left/right unbound). Right and up increase.
  - ControlModel (UI thread): onButton(ButtonEvent, timeSeconds) and tick(timeSeconds). It
    tracks the current tab, press times and modifiers, and produces commands and the held
    word as specified in the shared design: a press sends one Step at once; after 250 ms
    still held, the axis becomes "held" and the audio side ramps; release clears it. L1/R1
    change tab (wrapping) and clear any held d-pad axis. Y + a d-pad direction sends Reset
    for the knob bound to that direction (with X held, the X binding) and does not step.
    Select is the fine flag. Select + B sends ToggleSwitchLatch (and does not start a
    momentary hold). B alone holds the switch. A holds feedback maximum. L2/R2: a press
    sends one feedback Step, then the feedback ramp is held until release; both held = no
    movement. Opposite d-pad directions held together = no movement on that axis. Start
    does nothing in M2. It exposes the current tab and modifier state for the UI.
  - ButtonControlSource publishes, for the UI to read without locks: the 11 current knob
    values, the stored feedback value and whether maximum is active, the effective switch
    state and the latch, and a count of commands processed.
  - Time on the audio side is counted in control blocks (1/12000 s), never wall clock.
  - Determinism: the same sequence of commands and held words at the same block indices
    gives the same frames.

Acceptance criteria:
  1. With no input, every frame equals the ParamTable default positions with the switch
     off, and AudreyVoice driven by it for 10 s is bit-identical to AudreyVoice driven by a
     ScriptControlSource with an empty script.
  2. Unit tests for: tap step sizes for an ordinary knob, Frequency and feedback, coarse
     and fine; clamping at both ends; reset; the ramp (starts 250 ms after press, the
     stated speeds and acceleration within 1%, stops on release, fine is one eighth);
     feedback ramp rate; both-directions-held; feedback maximum (frame value 1.0 while
     held, stored value unchanged, restored on release); switch held, latched, and held
     while latched (XOR); every tab's bindings including X; tab change while a direction is
     held; Y + direction with and without X; Select + B.
  3. A threaded stress test: one thread pushes commands and held words as fast as it can
     for 2 seconds while another calls read() continuously; no crash, no sanitizer report
     (run under ThreadSanitizer in a third build directory as well as ASan/UBSan), the
     count of commands processed plus commands dropped equals commands sent, and final
     values are within 0..1.
  4. A test that read() performs zero operator new calls over at least 12000 blocks with
     commands arriving (same technique as tests/core/voice_alloc_test.cpp).
  5. A scripted end-to-end test: a list of timed button events (a rise of feedback with R2,
     a tab change, a held d-pad ramp, a momentary maximum, a switch hold) fed through
     ControlModel and ButtonControlSource into AudreyVoice for 20 s gives finite output,
     peak below 1.0, and the same output on two runs.

How to verify:
  cmake -S . -B build/host -DCMAKE_BUILD_TYPE=Release && cmake --build build/host -j
  ctest --test-dir build/host --output-on-failure
  cmake -S . -B build/asan -DCMAKE_BUILD_TYPE=Debug -DCMAKE_CXX_FLAGS="-fsanitize=address,undefined -fno-sanitize=signed-integer-overflow"
  cmake --build build/asan -j && ctest --test-dir build/asan --output-on-failure
  cmake -S . -B build/tsan -DCMAKE_BUILD_TYPE=RelWithDebInfo -DCMAKE_CXX_FLAGS="-fsanitize=thread"
  cmake --build build/tsan -j && ctest --test-dir build/tsan --output-on-failure -R control
  scripts/make_reference.sh --check        -> still passes (nothing in M1 changed)
  Passing = all tests pass in all three, no warnings, no sanitizer reports.

Report back: files added, full test output from the three builds, the measured ramp speeds,
  the exact layout of the held word, any behaviour the proposal left undefined and how you
  resolved it, deviations, and open questions.
```

## M2-B: audio host, input mapping and the application shell

```
Goal: `audreybrick` runs: it opens a window and an audio device, maps gamepad and keyboard
      to Button events, drives ControlModel and ButtonControlSource, and plays AudreyVoice
      through the SDL audio callback with meters, without any drawing beyond a cleared window.

Context: M2-A is merged (audrey_control: ControlModel, ButtonControlSource, Buttons.h).
      SDL2 2.32 is installed via Homebrew (`sdl2-config`); find it with CMake's
      find_package(SDL2) and fall back to sdl2-config/pkg-config. The device will provide
      its own libSDL2 (2.30 reported), so use only API available in SDL 2.0.18 or later and
      say which newest function you rely on.

Scope: src/platform/AudioHost.{h,cpp}, src/platform/InputMap.{h,cpp},
      src/platform/Denormals.h, src/platform/Meters.h, src/app/App.{h,cpp}, src/app/main.cpp,
      src/app/UiSnapshot.h, tests/platform/**, and CMake lines (a static library
      audrey_platform; the executable audreybrick; SDL must be optional at configure time:
      without SDL2 everything from M1 and M2-A still builds and tests, and the app target
      is skipped with a message).
Out of scope: drawing text or widgets (M2-C); src/core; src/control; audio input; presets;
      device packaging; config files.

Constraints:
  - The audio callback does only this: enable flush-to-zero once; convert nothing by hand
    (request float32 stereo); call AudreyVoice::process with the ButtonControlSource into
    two preallocated channel buffers sized at device open for the largest buffer SDL may
    deliver; interleave into SDL's buffer; update peak meters and the CPU measurement
    through atomics. No allocation, lock, I/O, logging or waiting. If SDL delivers more
    frames than the preallocated size, process in chunks; never allocate.
  - Device: 48000 Hz, AUDIO_F32SYS, 2 channels, 256 frames requested, allowed changes =
    SDL_AUDIO_ALLOW_SAMPLES_CHANGE only. Log the obtained spec once at start (on the main
    thread). Options: --buffer <frames>, --audio-driver <name> (sets SDL_AUDIODRIVER),
    --list-audio (print drivers and devices, exit).
  - AudreyVoice::init() and all allocation happen before the device is unpaused. Shutdown:
    pause and close the device before destroying the voice.
  - CPU meter: time spent in the callback divided by the buffer's duration, as a smoothed
    value and a maximum since last read, using SDL_GetPerformanceCounter. Under-run
    counting is not available from SDL; do not invent it.
  - Output meter: per-channel peak since last read, as atomics.
  - InputMap: SDL_CONTROLLERBUTTONDOWN/UP and SDL_CONTROLLERAXISMOTION for the triggers
    (L2/R2 are axes on most pads; threshold with hysteresis) and SDL_KEYDOWN/UP (ignore key
    repeat) to ButtonEvent, using SDL GameController names and the keyboard binding in the
    shared design. Open the first controller, handle hot-plug add/remove. One table holds
    all bindings. Never use raw joystick indices.
  - App: the main loop polls events, feeds ControlModel with a monotonic time, calls
    tick(), fills a UiSnapshot (current tab, modifiers, 11 values in normalised and engine
    units via ParamTable, feedback stored/max-active, switch state and latch, peaks, CPU,
    obtained audio spec, dropped-command count) and hands it to a `render(const UiSnapshot&)`
    function, which in this task only clears the window. Window 1024x768 logical size
    (SDL_RenderSetLogicalSize), resizable, vsync; if no vsync, cap at 60 Hz.
  - A headless self-test mode for automation: `audreybrick --selftest <button-script>
    --seconds <n>` runs with SDL_VIDEODRIVER=dummy and SDL_AUDIODRIVER=dummy acceptable,
    feeds timed ButtonEvents from a small text file (`<time_s> <button> <down|up>`),
    runs the real callback path for n seconds, then prints the final knob values, the
    maximum CPU figure and the output peak, and exits 0. Parsing happens before audio starts.
  - Exit: window close or Escape. Exit code 0 on a clean exit, non-zero with a message if
    the window or audio device cannot be opened.

Acceptance criteria:
  1. `audreybrick --list-audio` prints drivers and devices and exits 0.
  2. `audreybrick --selftest` with a script that raises feedback (R2 held 3 s) exits 0 and
     reports a FeedbackGain value consistent with the ramp rate and an output peak above
     0.01; the same script with the dummy audio driver gives the same final knob values.
  3. Unit tests (no window needed) for InputMap: each key and controller button maps to the
     right Button; trigger axis thresholds and hysteresis; key repeat ignored; unknown
     events ignored.
  4. A test of the callback function called directly (no SDL device) with buffer sizes 64,
     256, 1024 and one larger than the preallocated size: output equals AudreyVoice driven
     directly with the same control source, bit for bit, when flush-to-zero is disabled for
     the test; state whether enabling flush-to-zero changes any sample over 20 s of the
     feedback-rise script (informational).
  5. A test that the callback performs zero operator new calls.
  6. Without SDL2 available (configure with -DAUDREY_WITH_SDL=OFF), the tree configures,
     builds and passes all earlier tests.
  7. All tests pass under ASan/UBSan; the selftest runs clean under ThreadSanitizer.

How to verify: the three builds and ctest as in M2-A, plus
  build/host/audreybrick --list-audio
  build/host/audreybrick --selftest tests/platform/rise.txt --seconds 5
  SDL_AUDIODRIVER=dummy SDL_VIDEODRIVER=dummy build/host/audreybrick --selftest tests/platform/rise.txt --seconds 5
  cmake -S . -B build/nosdl -DAUDREY_WITH_SDL=OFF && cmake --build build/nosdl -j && ctest --test-dir build/nosdl
  scripts/make_reference.sh --check

Report back: files added, test output, the obtained audio spec on this Mac, measured callback
  CPU on this Mac at 256 frames, the newest SDL function used and the SDL version it needs,
  whether flush-to-zero changed any sample, deviations, open questions, and a short numbered
  checklist the human can run by ear on the Mac (the window will be blank in this task).
```

## M2-C: the screen

**Notes added after the M2-B review (2026-11-17), which apply to the brief below:**
- `UiSnapshot` (in `src/app/UiSnapshot.h`) already carries everything needed; do not add fields. What the renderer must derive itself: for Frequency the engine value is a MIDI note number and the unit text is `"note"`, so compute Hz (`440 * 2^((n - 69) / 12)`) and the note name; parameters whose unit text is empty (reverb mix, reverb decay, delay mix, repeats, volume) are shown as a percentage of their range or as their plain engine value, whichever reads better, stated in the report; which d-pad bindings are active comes from `Tabs.h` and the snapshot's `xHeld`.
- The snapshot's peaks cover only the time since the previous snapshot, so peak hold and decay for the meters live in the renderer.
- The original's limiter keeps the output well under full scale (the highest peak in any M1 render is 0.80), so a clip mark at 1.0 may never light in normal use. Draw it anyway, and scale the meter so ordinary levels (0.05 to 0.6) are easy to read.
- Show the stored feedback value even while maximum is held (it can move underneath), and mark clearly that maximum is active.
- The keyboard binding is a development aid; the screen shows the Brick's button names (L1, R1, L2, R2, A, B, X, Y, Select, d-pad), not keyboard keys.

## What the human tests at the end of M2 (on the Mac, by ear and by hand)

A numbered checklist is prepared with M2-B and finalised with M2-C. In outline: start the app; confirm silence; raise feedback with R2 until the drone starts; change tabs with L1/R1; move each parameter and hear it; hold A for the maximum; hold B and hear the delay warp; latch it with Select + B; fine adjust; reset; watch the CPU and output meters; leave it droning for ten minutes and listen for dropouts.
