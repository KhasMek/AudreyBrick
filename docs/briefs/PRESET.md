# PRESET: presets

Written 2026-11-23 by the orchestrator from the human's design. Three tasks, in this order: **PRESET-A** (the file format and the preset store, no UI), **PRESET-B** (the PRESET tab, the scrolling tab bar, Start + A), **PRESET-C** (user data moved out of the app folder). Read `CLAUDE.md`, `docs/ORCHESTRATION.md`, and for the existing patterns `docs/briefs/REC.md` (numbered files, messages, the Start chord) and `docs/briefs/MOD.md` (MOD-B and MOD-D: the tab and its gestures).

## The human's decisions (do not change)

1. A preset is **one JSON file** in a presets folder. Any number of them; the list scrolls.
2. A preset stores **the sound**: the eleven knobs (the stored value of each, including the stored feedback, not a momentary frame value), the latched state of the delay switch, and the four modulation slots (shape, target, rate, depth, polarity). It stores **nothing about the audio input**: loading never changes the source, the device, the file, the play mode or the input gain. Momentary states (A = MAX held, B held) are neither stored nor changed.
3. **No init patch.** The start-up state stays exactly as it is; nothing is loaded at launch.
4. Names: new presets are numbered, `preset-0001.json`, `preset-0002.json`, ... (the next number is the highest existing number + 1, as the recordings do). The list shows every `*.json` in the folder by file name without the extension, so a file renamed on a computer shows its new name. No on-screen keyboard.
5. A **PRESET tab**, last, after MOD. The tab bar no longer fits all tabs, so it **scrolls sideways** (below).
6. **Start + A on any tab saves a new preset** (the "freeze" of the original plan), like Start + Y records.
7. Gestures on the tab (a first pass, to be judged on the device): up/down move through the list (hold to scroll); the top entry is `SAVE NEW`; **right** loads the highlighted preset (on `SAVE NEW`: saves a new one); **X held + right held about 1 second** overwrites the highlighted preset with the current state; **Y held + right held about 1 second** deletes it. A progress bar fills during the holds; releasing early does nothing. A short message confirms each load, save, overwrite, delete and each failure. The last loaded or saved preset stays marked in the list until something else is loaded or saved (it is not a claim that the current settings still equal it; do not track "modified").
8. Loading is audible by design: every stored setting jumps to the preset's value and the existing knob smoothing and modulation smoothing do the rest. No extra fade.
9. User data moves out of the app folder so an update cannot delete it (PRESET-C).

## PRESET-A: the format and the store

A new module (suggested `src/preset/`), no SDL, built in the no-SDL configuration, tested on the host and in the Linux containers.

- **Format, version 1.** A JSON object with: a format marker and version (`"format": "audreybrick-preset"`, `"version": 1`), the app version that wrote it (informational), `"knobs"`: an object keyed by stable knob names (take them from the parameter table; define the eleven names once, document them), each the knob's stored normalised position 0..1; `"delaySwitch"`: boolean (the latch); `"mod"`: an array of four objects `{ "shape", "target", "rate", "depth", "polarity" }` using the script names for shape, target and polarity (as `ScriptControlSource` accepts; one canonical spelling when writing), `rate` the normalised rate 0..1, `depth` -1..+1. Numbers are written so that reading returns the identical float (`%.9g` or equivalent): save then load must restore every value bit for bit, and a render after load must equal a render with the same values set directly (test both).
- **Tolerant reading.** Unknown keys are ignored. A missing knob, switch or slot field keeps its **default** (the start-up value), not the current value: loading a preset always produces the same state whatever was set before. Values out of range are clamped; NaN/inf cannot be expressed in JSON and a number that parses to non-finite is an error. A wrong format marker, a version greater than 1, a syntax error, a wrong type, a file larger than 64 KiB or an unreadable file is a failure with a short reason; **nothing is applied from a file that fails** (parse completely first, then apply). Duplicate keys: last wins or error, your choice, say which.
- **JSON parser.** Write a small strict parser for what the format needs (objects, arrays, strings with escapes, numbers, true/false/null), bounded depth and size, no exceptions escaping, no recursion beyond the bound. No new third-party dependency. Test it hard (malformed input, truncation at every byte of a valid file, deep nesting, huge numbers, bad escapes, a UTF-8 BOM, CRLF) under ASan + UBSan.
- **Writing.** Write to a temporary file in the same folder, flush, close, then rename over the target, so a power cut leaves either the old file or the new one. Clean up a stale temporary file on the next scan. Report failures (folder missing, card full, read-only) with a reason; never leave a half-written `*.json`.
- **The store.** Scan the folder (`*.json`, case-insensitive extension, regular files only, no recursion), sort by name case-insensitively with numbers in natural order if cheap, cap the list (choose a cap of at least 2000, say what happens beyond it), compute the next `preset-NNNN.json` number (four digits, growing wider past 9999 is fine), delete a preset, and re-scan after each change. A missing folder is an empty list plus a state the UI can show, not a crash; saving creates the folder if it can.
- **A plain data type** for a preset's content, independent of the app's classes, plus functions to capture it from and apply it to the things that hold the state. Find where the stored knob values, the switch latch and the modulation settings live (`ButtonControlSource` / the control model, `ModPanel` / `ModUiPort`) and design the capture/apply seam so PRESET-B only calls it; if capture/apply needs app classes, put that glue where it can still be tested without SDL. Applying must go through the same paths a user's change takes (so the UI, the engine and the half-second mod log all agree), release any ramps in progress, and be safe while audio runs: nothing new on the audio thread, no allocation, lock or I/O there.
- **Threads.** All file work happens off the audio thread. Files are tiny; the UI thread is acceptable if a slow card (single writes of up to 28 ms were measured) can only cost a frame, never audio. Say what you chose.
- **Tools and scripts.** `audrey_render` (or a small tool of its own) gets a way to write a preset from a script's end state and to render starting from a preset, so the round trip is testable from the command line. Add a `reference/` style check only if it comes cheaply; the 25 reference hashes and the 12 mod-set hashes must not change.
- **Documents.** `docs/PRESET_FORMAT.md`: the format with a complete example, every name, the reading rules. `docs/PARAMETERS.md` gets a pointer.

Tests required: round trip exact for every field at defaults, extremes and random values; every reading rule above; every failure leaves the state untouched; atomic write (inject a failure between write and rename); numbering (gaps, renamed files, non-numbered names, 9999); scan order and cap; delete; folder missing/unwritable; render equality after load; the parser tests.

## PRESET-B: the tab, the tab bar, Start + A

- **`Tab::Preset`**, last. L1 from LOOP now lands on PRESET; adapt every button script that counts L1 presses from LOOP (`tests/platform/*.txt`, `tests/mod/mod_tab.txt`, `docker/knulli_rootfs_tests.sh`) and say which you changed.
- **Scrolling tab bar.** The bar keeps its text size. It shows as many tabs as fit and slides so that the selected tab is fully visible **together with its neighbour on each side** (at the ends of the tab order: the first or last tab sits at the bar's edge; L1/R1 still wrap round). A small marker at either end shows that tabs are hidden there. No animation is needed; if you add one it must not delay input. Tab order and L1/R1 behaviour are otherwise unchanged. Show in screenshots every tab selected in turn.
- **The tab's screen**, in the style of the MOD tab and the INPUT file list: the list with `SAVE NEW` on top, the highlighted entry, the marked (last loaded/saved) entry, a count (`12 PRESETS`), scroll indication, long names cut cleanly, the hold progress bar with what it will do (`OVERWRITE PRESET-0007`, `DELETE PRESET-0007`), the message line (`LOADED ...`, `SAVED ...`, `DELETED ...`, `LOAD FAILED: <reason>`, ...), an empty-folder state and a folder-missing state. The feedback strip, meters, parameter strip and footer stay as on every tab; the footer's cells say what X and Y do here.
- **Gestures** as decided (item 7). Details: the hold time is about 1 second and its bar must be clearly visible; pressing or releasing X or Y, or releasing right, cancels a hold and makes held directions inert until released (the MOD-D rules; reuse the pattern, including "a modifier pressed on another tab does not count" and dropping modifier state on L1/R1 and `releaseAll`); X + right and Y + right on `SAVE NEW` do nothing; with both X and Y held nothing happens; Select has no meaning here; up/down repeat at the INPUT lists' rate, capped at one step per update. After a delete the highlight moves to the next entry (or the previous at the end); after a save the new entry is highlighted and marked. The list is re-scanned when the tab is entered and after each change, not every frame.
- **Start + A** on any tab saves a new preset (either press order, as Start + Y; A's own function, MAX, must not fire as part of the chord in a way that changes the stored feedback, and the chord's A must not be captured as "MAX held"; say how you handle A pressed first, since MAX is momentary and audible). A message (`SAVED PRESET-0008`) shows on whatever tab is current, where the recorder's messages show; if both have something to say, define the priority. Start + A works while recording and while a pop-up is open on INPUT (as Start + Y does).
- **App options.** `--preset-dir <dir>` (default: none; the tab then shows that no folder is set and Start + A reports it); self-test hooks in the style of the existing ones so that load, save, overwrite, delete and Start + A can be driven and checked from button scripts without a display, including through the packaged launcher.
- **Logging:** one line per load, save, overwrite, delete and failure (file, reason), and the folder and preset count at start.
- **Documents:** `docs/CONTROL_SCHEME_PROPOSAL.md`, `packaging/README.txt` (a Presets section: the folder, the file names, renaming on a computer, what a preset holds and what it does not, that loading is audible), and a device checklist `docs/PRESET_RUN_BRICK.md` in the style of `docs/MOD_RUN_BRICK.md` (numbered steps with exact presses; include: save, load restores sound and modulation, overwrite, delete, Start + A on several tabs and while recording, a renamed file and a deliberately broken file put on the card from the computer, many presets for scrolling, the tab bar on every tab, loading a loud preset from silence, quitting and finding the presets again, and the opinions wanted: gestures, hold time, the scrolling bar, whether right-to-load is too easy to hit by accident).

Tests required: panel logic for every gesture and cancellation above; router tests for the chord and the tab; layout tests and screenshots for every state and for the tab bar on each tab; a button-script self-test through the app; the existing suites adapted.

## PRESET-C: user data out of the app folder

Today everything the user owns is in `roms/ports/audreybrick/data/` (logs, `input/`, `recordings/`, the run counter) and replacing the app folder on an update deletes it. The card is not ext4, so no symlinks.

- **New location on KNULLI: `/userdata/saves/audreybrick/`** ([confirmed, read from the image]: KNULLI's data initialisation creates `/userdata/saves`; the ports system lists only `.sh` and `.squashfs`, so folders do not appear as games). It holds `input/`, `recordings/`, `presets/` (new) and the logs, laid out as `data/` is now.
- The launcher (`packaging/AudreyBrick.sh`) chooses the data folder: `/userdata/saves/audreybrick` when `/userdata/saves` exists and is writable; otherwise `data/` inside the app folder as now (other firmwares, tests); the existing `/tmp` fallback for logs stays last. An environment variable may override it for tests. It passes `--preset-dir`, `--input-dir` and `--record-dir` accordingly and creates `presets/`.
- **One-time move.** If the new folder is in use and `audreybrick/data/` exists with content, move the content across before the app starts: never overwrite an existing file in the new place (keep both; say how names are resolved), never delete anything that was not moved successfully, survive being interrupted (running it again finishes the job), log what was moved, and handle a 300 MB recording without copying it where a rename within the same partition will do. Recording numbering and the run counter must continue correctly after the move. The launcher's existing promise about what it creates and deletes (its header comment) must be rewritten to match, and stay as narrow.
- **The package ships no `data` folder** (check what `scripts/package_port.sh` / `make_port.sh` put in `dist/`), so replacing `audreybrick` is harmless from now on.
- Adapt `docker/knulli_rootfs_tests.sh` and `scripts/test_on_knulli_rootfs.sh` (the root filesystem there may lack `/userdata/saves`: test both branches, the move with and without conflicts, an interrupted move, an unwritable target) and keep the PASS/FAIL counting format. Update `packaging/README.txt`, and every checklist in `docs/` that names `roms/ports/audreybrick/data/` (add a note at the top of the old ones rather than rewriting history; `docs/PRESET_RUN_BRICK.md` gets the new paths and a first step that checks the move happened and nothing was lost).

## PRESET-D: remove the one-time move (the human's decision, 2026-11-23)

The human is the only user, and their card has already been moved. The move code is the riskiest part of the launcher (it renames and deletes user files) and serves a case that cannot recur. **Remove it entirely.**

- **Remove from `packaging/AudreyBrick.sh`:** the move of `audreybrick/data/` into the new folder, its recovery at start, the transit / info / marker files, `data-move.log`, the safe-name and found-file handling, the sync calls that belong to it, and every helper used only by them. The launcher must never rename, move or delete anything inside an old `audreybrick/data/`, nor any file it did not create itself.
- **Keep:** the data folder choice (`/userdata/saves/audreybrick` when usable, else `data/` in the app folder, `/tmp/audreybrick-data` for logs last; `AUDREY_SAVES_DIR`), `--preset-dir`, the run counter, and the log rotation **with its no-overwrite behaviour** (free name, `mv -n -T`, the app's log never opened over an old one, `stdout.log` appended). The package still ships no `data` folder.
- **Add one notice:** when the data folder in use is not the app's `data/` and `audreybrick/data/` exists and holds anything, write one `launcher:` line to stdout.log (and one line to stderr) saying that files were found in the old folder, that they are left untouched, and where to move them by hand. No more than a cheap emptiness test; nothing is changed on disk.
- **Tests:** delete the tests of the move, recovery, kill sweep, FAT section and their helpers (the privileged container and the `hdiutil` images go too, unless something kept still needs them). Keep and, where needed, adapt the tests of the folder choice, the fallbacks, the log rotation (L1 to L4 or their equivalents) and the presets folder. Add tests for the notice: old `data/` with content is byte-for-byte and name-for-name unchanged after two starts, the notice appears each time; empty or absent old `data/` gives no notice; when the app's `data/` is itself the data folder there is no notice.
- **Documents:** `packaging/README.txt` (remove "Moving from audreybrick/data" and the one-time update warning; say plainly where files live, that replacing the `audreybrick` folder is safe, and that an old `data/` folder is left alone and can be moved by hand), the launcher's header comment, `docs/PRESET_RUN_BRICK.md` (remove the STOP box and the move steps and log lines; keep a short step: check that `saves/audreybrick/` holds the files), the dated notes on top of the older `docs/*_RUN_BRICK.md` (they say the first start moves the old folder by itself: no longer true).
- Report: lines removed, the launcher's process count and time on a normal start before and after, the PASS / FAIL counts of `scripts/make_port.sh`, and an audit list of every `mv`, `rm`, `rmdir` and truncating `>` left in the launcher.
